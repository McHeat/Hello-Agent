# RAG 落地注意事项

## 一、Top-K 不是越大越好

典型做法是向量检索与 BM25 组成混合召回，先粗召回三十到五十条候选，再交给交叉编码器
（Cross-Encoder）精排到三到五条，只有精排后的这几条才允许进入提示词。直接把粗召回的
几十条全部塞进提示词，性价比很差：一方面无关内容会稀释关键信息并消耗大量 token，
另一方面长上下文会触发 Lost in the Middle，模型容易忽略埋在中间的证据。混合召回之所以
有效，是因为稠密向量擅长语义近似，而 BM25 擅长型号、错误码、专有名词这类精确词匹配，
两者互补。多路结果的融合常用 RRF（Reciprocal Rank Fusion），它只依赖名次而不依赖
各通路分数的量纲，因此余弦分与 BM25 分可以直接混用。

## 二、chunk 大小的两难与父子切分

块太大，一个块里会混进多个主题，检索粒度变粗，embedding 被多主题平均后反而不准；
块太小，上下文被切断，跨句依赖丢失，模型只看到半句话。主流解法是父子切分，也叫
Small-to-Big：用小片段去做检索，命中之后把它所在的大段落完整返回。具体做法是先把
文档切成较大的父块，再在每个父块内部切成带重叠的小子块，只把子块向量化并写入向量库，
子块的元数据里记录父块 ID。检索时命中子块，再按父块 ID 从父块存储中取回大段落，
并按父块去重，避免同一段落被多个子块重复塞进上下文。这样同时拿到了检索精度与上下文
完整性。子块之间保留一定重叠，是为了防止一句话恰好被切在两个块的边界上。

## 三、Lost in the Middle

检索到的片段不要埋进超长上下文的中间，关键片段尽量放在开头或结尾，因为近因效应更强。
常见做法是把最相关的片段放在开头、次相关的放在结尾、最不相关的放在中间，形成 U 形的
相关性分布；同时在提示词末尾重复一次问题，把用户意图放在最近的位置。此外还要设置
上下文字符预算，超预算时优先砍掉中间的低相关片段，而不是截断头尾的关键证据。

## 四、用指标量化，别拍脑袋调参

召回用 Context Recall（该检到的检到没）、精度用 Context Precision（检回的有多少真相关）
分开看，并且要在不同阶段度量：Context Recall 应该在粗召回阶段计算，因为粗召回漏掉的
文档后面再精排也救不回来；Context Precision 应该在精排之后、真正进入提示词的列表上
计算，它直接决定 token 是否被浪费。配合一个几十到几百条的人工标注 Golden Set 做回归，
每次改参数都跑一遍，和基线比较指标跌幅，超过阈值就让持续集成失败。想验证某个组件
到底有没有收益，可以换成空实现做消融实验，用同一套指标对比。

## 五、兜底链路

召回不足时要有降级：先扩大 Top-K 重试，重试用尽仍然证据不足就转人工，或者如实告诉
用户没有找到相关信息。RAG 稳不稳，往往取决于检索失败时兜得全不全，而不是检索多准。
实现上要设置重试次数上限与 Top-K 硬上限，防止无限放大；每一档降级动作都要记录下来
方便审计；判定为转人工或如实回答时，绝不能把空的或低质量的上下文交给大模型自由发挥，
否则会产生看似流畅却毫无依据的幻觉答案。
