RAG具体落地时的几个权衡点：
+ Top-K 不是越大越好：典型做法是向量 + BM25 混合召回 Top-30~50，再用交叉编码器（Cross-Encoder）精排到 Top-3~5 才进 prompt。直接拿粗召回的几十条全塞进去，性价比很差。
+ chunk 大小的两难：块太大 → 一个块混多个主题、检索粒度粗；块太小 → 上下文被切断、丢失跨句依赖。主流解法是父子切分（Small-to-Big）——用小片段去检索（准），命中后把所在大段落返回（完整）。
+ Lost in the Middle：检索片段别埋进超长上下文中间，关键片段尽量放开头或结尾（近因效应更强）。
+ 用指标量化，别拍脑袋调：召回用 Context Recall（该检到的检到没）、精度用 Context Precision（检回的有多少真相关）分开看，配合一个几十到几百条的人工标注 Golden Set 做回归。
+ 兜底链路：召回不足时要有降级——扩 Top-K 重试、转人工、或如实说"没找到相关信息"。RAG 稳不稳，往往取决于"检索失败时兜得全不全"，而非"检索多准"。
