## 一、改造目标的明确性 —— 评价：高

### 优点

- G1~G5 均为可判定目标（门禁生效且跨实现一致、生产档有重建流程、
  写放大 O(N²)→O(N)、能力清单、兼容性），且第三章明确列出了**非目标**，边界清晰；
- 1.3 节「已确认的三条边界」（范围 / 零依赖默认 / LLM 边界）把最容易扯皮的
  问题前置锁定；
- 1.5 节 12 个决策项（D1~D12）逐项给出建议方案 + 备选 + 影响，且标注了
  D2/D3/D7 是行为变更需重点确认——这是成熟方案的标志。

### 不足

1. **G2 缺少量化质量目标**。方案论证了「英文模型 vs 中文语料错配」，但未设定
   类似「生产档在中文 Golden Set 上 context_recall 相对默认档提升 ≥ X」的
   验收数值。当前验收只有「能加载、前缀生效、指纹拦截」，全是**机制正确性**
   验收，没有**效果**验收。G4 同理（查询变换、缓存均无质量/收益指标，
   仅有「关闭后行为一致」的反向验收）。
2. G3 的 O(N) 目标可度量，但**未附带基准场景**（如「10 万子块、batch 32 的
   构建耗时/写次数前后对比」），验收条款「写次数为常数级」是对的，
   建议补一个具体的基准规模声明。

## 二、改造方案与评估报告结论的一致性 —— 评价：高度一致，且多处超越

| 评估报告结论 | 方案处理 | 一致性判断 |
|---|---|---|
| P0-1 sigmoid 归一化 + 非零阈值 | 升级为**接口级 `normalize_scores()` 契约**（D1），并指出报告建议的「仅 CE 加 sigmoid」不够——因为 lexical 与 noop 分数域同样不一致 | **超越报告**。核验属实：`NoopReranker` 用 RRF 分（≈0.016），`lexical` 含 prior 地板，仅修 CE 确实不完整 |

| 报告建议阈值「0.3~0.5 扫描」 | 方案指出该建议**缺少数据基础**（Golden Set 无负样本、无拒答指标），先补负样本与 `--sweep-threshold` 再定值（D4 不预拍板） | **修正了报告的一个疏漏**，处置正确 |
| P0-3 写放大 | 最小修复 + SQLite 选项 + `auto_save` 默认值变更（D7），与报告建议一致 | 一致 |

| P2 与缺失 #9~#12 | 第十一章全部列入后续路线并给出触发时机 | 一致，范围裁剪合理 |

## 三、关键改进点的覆盖情况 —— 评价：范围内完整，边界外有意识地留白

### P0+P1 范围内：全覆盖，无遗漏

报告的 12 项缺失在方案第 2.4 节映射表中逐项有归宿（处理 / 延后 / 不做），
不存在「报告指出但方案静默忽略」的项。

### 覆盖质量上的三个亮点

1. `production.json` 必须显式写全 params 的提醒（决策 2「执行要点」）——
   这是对现有 `_reconcile_component_params` 换实现丢弃继承参数行为的正确预判，
   核验 `config.py:420-455` 确认该风险真实存在；
2. 负样本 GoldenCase 兼容旧 JSON（`answerable` 默认 True、负样本允许空
   `relevant_ids`）——核验现有校验（`test_09` 中空 `relevant_ids` 会被拒），
   方案确实需要且只放宽了这一处；
3. `GATED_METRICS` 新增指标在旧基线缺失时跳过比较——核验
   `runner.py:160-161` 的 `if metric not in base_summary: continue`，
   该兼容路径存在，方案判断正确。

### 覆盖缺口（范围内）

- **`RetrievalResult.coarse` 的分数域未纳入契约**。`retrieval/pipeline.py:119-128`
  构造 coarse `ScoredChunk` 时直接用 RRF 融合分（≈0.016 量级）。D2 改造后，
  同一结果对象里 `final[i].score ∈ [0,1]` 而 `coarse[i].score` 仍是 RRF 域，
  两套量纲并存。方案未提及是疏漏还是有意为之——需要明确
  （至少文档标注 coarse 为融合域）。

## 四、潜在风险与遗留问题

### 4.1 方案未识别的风险（本轮评审新发现）

1. **D7 会破坏 `test_05`，且方案的测试改动清单漏列了它**。
   `tests/test_05_embeddings_vectorstore.py:105-113` 的
   `test_persists_across_instances`：第一个实例 `upsert` 后立即用第二个实例
   从文件加载并断言 `count() == 1`。`auto_save` 默认改 `False` 后
   **文件根本不会被写入**，该测试必挂。方案的 MODIFY 测试清单只列了
   `test_01/08/09/10`。影响小（改测试或显式 `flush()` 即可），
   但直接冲击「122 个既有测试全绿」的验收承诺，必须补进清单。

2. **生产档阈值无法在 CI 内标定（最重要的一条）**。
   9.1 节的标定流程跑在**默认栈**（lexical + hashing）上，而 lexical 的
   分数分布（相关 ≈0.53 / 无关 ≈0.40，可分带仅 ~0.13）与生产栈
   （bge-reranker + sigmoid）**完全不同**——在默认栈上标出的阈值对生产栈
   **不可迁移**。方案在 `production.json` 里写了「标定后的阈值」，但全篇
   没有说明这个值由谁、用什么模型、在什么数据上标定（第 3.2 节明确
   「不要求下载真实模型」，测试全用假模型）。**若不补一个一次性的生产栈
   标定流程，G1 在生产档上只是「机制上生效」，阈值本身是无依据的拍脑袋值**。

3. **`NoopReranker` 归一化映射未定义，消融场景可能被阈值团灭**。
   「基于名次的单调映射」若沿用 RRF 量级（≈0.016），任何非零
   `min_best_score` 都会让 noop 消融实验全部拒答。需要明确策略：
   要么映射拉伸到 [0,1]（如 `1 - rank/n`），要么规定 noop 场景下阈值旁路。

4. **并行召回的性能承诺在默认栈上不成立**。
   `max(T_dense, T_sparse)` 只在 I/O-bound（API embedding）时成立；
   默认栈两路都是纯 Python CPU-bound（哈希 embedding + BM25 扫描），
   受 GIL 限制线程并行**无收益甚至更慢**。D10 建议改为「默认关闭、
   生产档/服务化显式开启」更稳妥（方案自己已列出此备选）。

5. **标定样本量过小**。8 正 + 3~5 负的 Golden Set，阈值置信区间极宽，
   某个阈值「零误杀」很可能只是样本运气。建议在方案中明确标注
   「阈值为暂行值，Golden Set 扩至 30~50 条后复标」。

### 4.2 方案已识别且缓解得当的风险

归一化波及断言（已列 code-explorer 前置梳理）、params 重置丢配置
（已加测试断言）、缓存脏读（index_version 键）、线程安全（RLock + 开关回退）、
可选依赖污染（延迟导入）——缓解措施与风险等级匹配，功能开关矩阵（10.1）
提供了不回滚代码的降级路径，设计合格。

补充一点有利核验：`test_07` 的断言形式全部是**顺序断言**
（`result[0].chunk.id == "c2"`）而非精确分数断言，D3 移除 prior 地板后
大概率不破；`test_09` 的 `_item` 用关键字构造 `ScoredChunk`，
`raw_score` 带默认值尾加完全兼容。D2/D3 的实际爆炸半径比方案自述的还要小一些。

### 4.3 遗留问题（范围外，方案已如实声明）

embedding API 重试（#9）、OTel（#10）、引用后校验（#11）、多租户安全（#12）、
ANN、BM25 倒排。其中 **#9 与生产档有交叉**：若生产档用 DashScope/OpenAI
而非本地模型，无重试的 embedding 调用会让离线构建很脆弱。建议至少在
`production.json` 文档中注明「云端 provider 场景需自行包一层重试」。

## 五、预期效果的验证方式与衡量标准 —— 评价：机制验证扎实，效果验证有盲区

### 做得好的

- 每阶段有独立验证条款 + 最终 11 项验收清单，可执行性强；
- 「8 条正样本零误杀」作为硬约束 + 拒答指标纳入 `GATED_METRICS` +
  `--gate` 锁定，形成了闭环；
- 「关闭所有可选组件后行为与现状完全一致」是很好的等价性验收；
- 向后兼容矩阵逐对象列明保障措施。

### 盲区

1. **无任何性能基准数字**。建议为 G3/G4 各定一个具体场景
   （如「10 万子块构建：改造前 N 次全量写 vs 改造后 1 次」、
   「API embedder 下两路召回 p95 延迟对比」），否则「O(N)」停在纸面；
2. **生产档质量验证完全缺位**（对应 4.1 第 2 条）：验收清单第 5~6 条只验证
   「能加载、能拦截」，没有「检索质量确实变好」的验证步骤。需补一条
   **一次性人工流程**：下载真实 BGE 模型 → 建索引 → 跑 Golden Set →
   记录基线 → 在此基线上标定生产阈值；
3. 「行为与现状完全一致」建议落成一个**可执行的等价性测试**
   （改造前后各跑一次 Golden Set，summary 逐项相等），而不是依赖人工判断。

## 七、总体结论

**方案能够达到预期效果，前提是补齐三件事。**

该方案与评估报告高度一致，且在归一化契约层次、模型指纹、负样本先行、
params 重置预判四处**超越了报告的原建议**，整体质量足以支撑
「按方案执行」的结论。预期效果中，P0-3（写放大）、G5（兼容性）、
P1 各项的机制性目标**可以高置信度达成**；P0-1 在**默认档**上可以达成
（标定流程设计正确）。

### 达成预期的三个前置条件

1. **补生产栈阈值标定流程**（Q1，最重要——否则 G1 在生产档上只是「看起来生效」）；
2. **把 `test_05` 补进测试改动清单**（否则「122 全绿」验收必挂）；
3. **明确 `NoopReranker` 映射与消融豁免策略**（否则消融工作流被阈值破坏）。
